# Gotchas & quirks (parsing rules, Hex CLI, app layout)

Consult these when you hit the relevant step. The parsing rules are correctness landmines — getting them wrong produces silently-wrong numbers, not errors.

---

## Parsing correctness rules (Mode)

- **Resolve every Liquid tag — nothing may dangle.** Mode SQL is saturated with Liquid: `{{ @param }}`, `{% form %}`, `{% if %}`, `{% assign %}`, `{% case %}`, `{{ @definition }}`, and Mode's built-in filters (`| date:`, `| default:`). Each must resolve to Hex Jinja + an input cell, an inlined value, or a CTE. A leftover `{{ @something }}` in a Hex SQL cell is not valid Hex Jinja and will error (or worse, silently mis-render). Sweep the whole query, not just the `WHERE`. → [`mode-semantics.md`](mode-semantics.md) §1.
- **Sweep every `{% if %}` / `{% case %}` branch — the query has multiple shapes.** A `{% form %}` select that swaps the `WHERE`, the `GROUP BY`, or the columns means the migrated cell must reproduce **all** branches (via Hex Jinja), not just the default. A branch that changes the **grain or population** is a fidelity risk — flag it 🔸 and prove each branch with a probe (see [`sql-review.md`](sql-review.md)).
- **Inline definitions and resolve dataset refs — don't leave dependencies dangling.** A `{{ @definition_name }}` must be inlined as a CTE or built as an upstream cell; a **dataset reference** to another report's query is a cross-report dependency that must be rebuilt upstream. A migrated cell that references an unresolved definition/dataset errors. Respect dependency order in the batch. → [`mode-semantics.md`](mode-semantics.md) §2.
- **The string-quoting rule is INVERTED from Mode — this is the #1 silent-zero-rows trap.** Mode makes you quote string params yourself (`'{{ @segment }}'`). **Hex auto-quotes string params**, so you must **drop** the quotes: `WHERE segment = {{ segment }}`. Leaving Mode's quotes in produces `''value''`, which matches nothing — the query **COMPLETEs but returns zero rows** (blank charts, no error). See the Hex CLI quirks below.
- **Don't re-query the warehouse from a ported notebook cell.** Mode notebook cells read *already-run* query results (`datasets['Query Name']`); the Hex Python cell must likewise read the upstream SQL cell's **dataframe**, not open a fresh warehouse connection — otherwise the numbers can drift from the gated SQL and you lose the single source of truth. → [`mode-semantics.md`](mode-semantics.md) §3.
- **Preserve field data types — dates especially.** Keep date columns as real DATEs end-to-end; don't cast a date to a string (it breaks the chart's date axis). Set the base-axis `dataType: DATE` and carry the grain as `truncUnit`. And **confirm a field's actual type against the warehouse** before applying date/number functions — a column named like a date (`closed_month`, a `..._period` bucket) may really be a NUMBER, so a date function errors or silently misleads. Probe the type against the connection (see the oracle below), don't trust the column name.
- **Maps: no native cell.** Build maps as a Python CODE cell (`px.scatter_geo(df, lat=, lon=, color=, size=, projection="natural earth")`), not an EXPLORE scatter of lat/lon.
- **The presentation layer is more than charts.** A Mode report holds **big-number tiles** (→ METRIC cells fed a 1-row SQL), **text/markdown blocks** (→ Markdown cells), **images** (→ Markdown cell via **file upload**, not URL), and — in bespoke HTML reports — **arbitrary HTML/CSS/JS and Chart.js/D3 embeds**. Native cells reproduce standard visuals + the row structure well; **custom CSS and hand-written D3/JS have no native equivalent → declare them as gaps with an agreed substitute** (approximating EXPLORE, a Python cell, markdown, or dropped) (⚠️), same bucket as maps. Don't silently drop tiles, and don't silently approximate a gap either.
- **A ratio of aggregates can't live in a native chart.** EXPLORE/METRIC aggregate **one column with one built-in aggregation** — there is no calculated measure. A Mode chart plotting margin %, conversion rate, or any `SUM(a)/SUM(b)` needs the **ratio pre-computed as a column in SQL** at that chart's grain (or a semantic-model MEASURE). Catch this during the parse; discovering it at build time means a SQL round-trip. → [`building-cells.md`](building-cells.md).
- **A field used only as a color/series split is still in use.** A dimension that appears *only* as a chart's color/series/group encoding (in the chart JSON, not the `SELECT` you first eyeballed) can look like a dead column and get dropped, silently killing the visual split. Rule of thumb: a column referenced *anywhere* in a chart def — including its encodings — stays in the SQL and on the chart.
- **Non-warehouse sources aren't recoverable from the SQL.** Uploaded CSVs, Google Sheets, and Mode helper datasets have no warehouse rows behind them — **ask the customer for the source** (file/CSV or where it now lives); never fabricate the values. → [`connection-mapping.md`](connection-mapping.md) §6.
- **Report parameters live in `{% form %}`, and the same report can have several.** Sweep for **all** `{% form %}` fields (they can be spread across queries), map each to one Hex INPUT cell, and place them **upstream** of the SQL that reads them (dependency-graph rule below).

## Hex CLI quirks (confirmed)

- `hex cell create` makes **only** code/sql/markdown cells. Everything else is authored via **YAML export → edit → import** (see `building-cells.md`): native viz cells (METRIC/EXPLORE/PIVOT/…), **INPUT (parameter) cells**, and **connection-less dataframe-SQL companion cells** (`dataFrameCell: true`, `dataConnectionId: null`, e.g. a KPI or ratio that reads a shared dataframe). All three are common in a migration — plan on one YAML round-trip for the parameters + companions + charts. (Get the input-cell / dataframe-cell shapes right by validating against the Hex JSON schema — `https://static.hex.site/hex-file-schema.json`; the `InputCell`/`InputCellConfig` defs give the `inputType`/`outputType`/`defaultValue`/`options` fields.)
- **A project assembled purely in YAML must register its data connection.** `hex cell create --data-connection-id` attaches the connection to the project automatically, but cells authored only in an imported YAML do not — the project's `sharedAssets.dataConnections` stays empty, so every SQL cell references a connection the project doesn't have and the run **ERRORs with no useful CLI detail**. Add the connection under `sharedAssets.dataConnections` before importing.
- **Hex auto-quotes string parameters in SQL Jinja — don't add your own quotes (INVERTED from Mode).** A `{{ var }}` referencing a STRING input renders as a *quoted* literal (`'value'`); wrapping it as `'{{ var }}'` produces `''value''`, which the warehouse reads as the literal string `'value'` (quotes included) and matches nothing — the query **COMPLETEs but returns zero rows** (blank charts, no error, so the COMPLETED/ERRORED oracle won't catch it). Reference string params bare (`{{ var }} = 'All'`); numeric params inject unquoted too. **When porting Mode SQL, strip the quotes Mode required around `{{ @param }}`.**
- **Hex runs cells as a dependency graph — input parameters must be UPSTREAM of their consumers.** A cell that references an input via `{{ var }}` depends on that input cell, so the **input parameter cell must come *before* (upstream of) every cell that uses it**. Place input cells at the top of the notebook (or at least above the shared SQL). An input placed **after** its consumer leaves the variable unresolved and the run **ERRORs**. Same rule when assembling `cells[]` in YAML: order input cells ahead of the SQL that reads them.
- **Reading cell output — `--with-output` returns the rows.** `hex cell run <cell_id> --with-output` waits for the run and **prints the result rows** (row count + values), so you can read the actual grain, counts, and samples. `cell get` still only returns source, and plain `run status` still only returns COMPLETED/ERRORED/timing. ⚠️ **Cell-id gotcha:** after a **YAML import**, `hex cell run` expects the **API cell id from `hex cell list`**, not the `cellId` shown in the export (they differ); a stale/export id returns `Forbidden`. Cells made by `hex cell create` return their runnable id directly.
- **The COMPLETED-vs-ERRORED boolean oracle** is still the fastest way to validate SQL, probe schema, and check type-casts (a bogus table → ERRORED). Run one probe per question with **`hex cell run <cell_id>`** (a single cell + its deps) so a failure isolates to that cell — `hex run status <project_id> <run_id> --watch` blocks until COMPLETED/ERRORED. (With `--with-output` you can now *also read the value*.)
  - **Type probe:** `SELECT YEAR(<col>) FROM <table> LIMIT 1` → ERRORED means `<col>` isn't a real date.
  - **Row-existence probe:** `SELECT 1.0/COUNT(*) FROM (<your query>)` → **ERRORED = zero rows** (divide-by-zero), COMPLETED = has rows. Catches an empty result (e.g. a mis-wired param that filtered everything out, or the `''value''` quoted-Jinja trap) even though you can't read values.
  - **⚠️ ERRORED is ambiguous — anchor the oracle before trusting a probe.** ERRORED does **not** mean only "div-by-zero / zero rows." A **row-level expression error** — a date function on an unexpected type, a numeric overflow, a bad cast — *also* returns ERRORED, indistinguishable from the signal you're probing for. So a probe can **falsely "confirm"** a wrong hypothesis by throwing for an unrelated reason. Guard it two ways: **(1) run anchor probes first** — a known-COMPLETED (`SELECT 1`) and a known-ERRORED (`SELECT 1/0`) — to prove the oracle is responding sanely; **(2) prefer assertions that can't throw at the row level** — aggregate comparisons via `GROUP BY … HAVING` or a scalar `CASE WHEN <agg> … THEN 1 ELSE 0 END`, never row-wise arithmetic that can overflow or type-error on the data. When a probe ERRORs, rule out a row-level throw before concluding your assertion failed.
  - **⚠️ Clean up probe cells before handoff.** These oracle/probe cells are throwaway scaffolding, not migration output — `hex cell delete <cell_id>` them (or trash the scratch project) once validated, so the delivered project holds only the real SQL + chart cells.
- `project run` / `cell run` are **async** — no `--no-wait`; poll `run status`. `cell update` has no `-t` flag.
- **⚠️ Markdown cells Jinja-render `{{ }}` — wrap injected reference text in `{% raw %}`. (Extra-critical for Mode.)** A markdown cell "runs": Hex evaluates `{{ var }}` interpolation in it. **Mode source you inject as reference — the raw query SQL and the report JSON — is *full* of Liquid `{{ @param }}` and `{% form %}` / `{% if %}` tokens**, and the migration brief + styling spec add more. On `hex project run` an unwrapped markdown cell ERRORs on the stray Jinja/Liquid (an empty or unknown `{{ }}` is a hard syntax error) and **fails the whole run while every SQL cell is fine** — a confusing "the reference cell is erroring?" symptom. Fix: wrap the injected body in `{% raw %}` … `{% endraw %}` (Jinja skips it; markdown still renders). Applies to any injected reference cell whose text contains braces — for Mode that's essentially all of them.
- Freshly imported versions have **no outputs** until you `hex project run` — charts render blank until then.
- **The notebook agent IS drivable from the CLI** — `hex thread create "<prompt>" --project <id>` starts it, `hex thread continue <id> "<prompt>"` iterates, `hex thread get <id>` polls status (needs the headless-agent-threads feature). This is the **default** Phase-2 viz build-out; see SKILL.md step 5. Point it at the project only **after** the QA'd SQL cells exist (pre-built path) or let it build them (agent path).
  - **`--json` returns a `url` — surface it to the customer immediately** so they can watch the build live and stop/redirect it. The build takes several minutes; don't leave it a silent black box.
  - **Its output form follows the prompt — there's no CLI flag for it.** A prompt that **opens** with "Build this as a GENERATIVE APP…" → a **custom code app** (`genAppFiles` in the export) — **not** what this skill wants. A **chart-type-prescriptive** prompt (name the cell type per tile, say *"native notebook cells … do NOT build a Generative app"*) → **native EXPLORE/METRIC/pivot cells + an `appLayout`** — the **deliverable here**. **Always verify the form after building** (`hex project export` → `genAppFiles` **empty/absent**, native `cellType`s present, `appLayout.tabs[].rows[]` populated); **re-prompt if it built a generative app**. Keep the SQL native + gated regardless.
  - **It may or may not assemble the app layout.** Native cells can exist in the notebook with an empty `appLayout` — the app view is then unbuilt. Ask for the layout explicitly in the prompt, verify it in the export, and fix it either by `hex thread continue` or the export → edit `appLayout` → import round-trip below (often faster).
  - **Watch for one pre-aggregated SQL cell per chart.** That's Mode's own anti-pattern carried across. Tell it to **consolidate** — one SQL cell at the finest grain the cluster needs, feeding many charts (`mode-semantics.md` §Consolidate) — and check the export.
  - **It respects "use these cells, don't rewrite SQL."** Given named dataframes + that instruction, it leaves the SQL/param cells untouched and binds charts to them (confirmed via export diff). Always verify with a post-build export.

## App layout (first-class in this build)

> The classic app **is** an `appLayout` over native cells, so this section applies to
> every migration here — whether the notebook agent assembled the layout or you did.
> Even on the delegated path, an export → edit `appLayout` → import round-trip is often
> the fastest way to fix row order, column spans, a fixed-height chart, or a reference
> cell that leaked into the app.

App layout **is** settable via CLI: `hex project export <id> -o f.yaml` → edit the `appLayout` block → `hex project import f.yaml`. Import matches by `projectId`/`sourceVersionId` (both DO NOT CHANGE) and updates in place as a new version.

Schema: `appLayout.tabs[].rows[].columns[]`; a column has `start`/`end` (0–120 grid) + `elements[]`; each element = `{type: CELL, cellId, showLabel, showSource, hideOutput, height}`. Use the **export's** cellIds (they differ from `hex cell` API ids). If an `appLayout` element points at a cellId that isn't present in the file, Hex **silently discards the custom layout and falls back to a default that includes every cell** — so the reference/source cells reappear in the app. Build the layout from a fresh export. Map cells by **position/order** (stable), not by content-sniffing. **Never put the Mode source-reference cells or the raw SQL cells in the `appLayout`** — leave them in the notebook (they're working references), and build the app layout from only the native chart/KPI cells.

- ⚠️ **Never set a fixed `height` on a chart-type EXPLORE element — leave it `null` (auto).** A small fixed `height` collapses the chart body to near-zero, so the app shows the cell's title with no chart under it. METRIC tiles and pivot/table cells tolerate a fixed `height`; **chart-type EXPLOREs do not** — let them auto-size.

### Mirror the source report's layout (polish)
Reproduce Mode's arrangement rather than inventing one. Read the layout from the Report Builder layout JSON (or the HTML report's structure):
- **Rows:** group tiles into the report's rows, ordered left→right.
- **Columns:** map each tile's width proportionally onto Hex's 0–120 grid — two half-width tiles → `0–60` and `60–120`; a full-width tile → `0–120`.
- **Bands:** keep big-number KPI tiles, filters, and inputs where Mode placed them (usually a top band); make the hero chart largest.
- **Height:** mirror the *horizontal* structure (rows + column spans) but let chart height **auto-size** (`null`, per the rule above).

> **UI gotcha:** after importing an appLayout, the Hex app view still shows the empty "build an app" onboarding screen — click **"edit app manually"** once to reveal it. The import worked; this is just a UI acknowledgment.
